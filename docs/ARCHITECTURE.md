# Winter Desktop — Архитектура

Статус документа: **актуально после MVP** (этапы 1–2 ТЗ; часть этапа 5) и первого
инкремента этапа 3 (снежки и снеговики).
Последнее обновление: 17.11.2026.

Ссылки на требования: `§N` — раздел `docs/TECHNICAL_SPEC.md`.

---

## 1. Цели и ограничения архитектуры

| Требование | Архитектурное следствие |
|---|---|
| 60 FPS, аппаратное ускорение (§3.10, §7) | Рендер только через D3D11/D2D, отдельный render-thread, zero-alloc в кадре |
| Click-through, но с возможностью взаимодействия (§3.8) | Переключаемый стиль окна + `WM_NCHITTEST` |
| Снег «на окнах» без чтения содержимого (§3.2) | Только `DwmGetWindowAttribute`/`GetWindowRect` — геометрия |
| Смена настроек без перезапуска (§3.1) | Настройки живут в `SettingsStore`, движки читают snapshot каждый кадр |
| Несколько мониторов / смешанный DPI (§3.9) | Один overlay-хост на монитор, физические пиксели, PerMonitorV2 |
| Устойчивость к сбоям (§5, §7) | Настройки: атомарная запись + fallback на дефолты; ошибки рендера не убивают процесс |
| Будущий macOS (§1.2) | Ядро (Core/SnowEngine) — без Win32, чистый .NET |

**Жёсткие запреты:** Electron/browser-based shell, платные библиотеки, имитация функций
заглушками, чтение содержимого чужих окон.

## 2. Карта модулей

Требуемые ТЗ модули (§6) реализованы как пространства имён/сборки; часть из них —
отдельные .NET-проекты, часть — папки внутри сборки, если граница «проект» не даёт
выигрыша (меньше церемоний, тот же уровень связности).

                          │  App / Tray / UI / Wiring  │
                          └───────────┬────────────────┘
              ┌───────────────┬────────┴────────┬────────────────┐
              ▼               ▼                 ▼                ▼
     ┌────────────────┐ ┌──────────────┐ ┌─────────────┐ ┌──────────────┐
     │  Interaction   │ │  Renderer    │ │  Platform   │ │   Settings   │
     │  (wiring in    │ │ D3D11+D2D+   │ │ Win32:      │ │ JSON store   │
     │   App, logic   │ │ DComp overlay│ │ tracker,    │ │ atomic write │
     │   in SnowEngine│ │              │ │ monitors,   │ │ migrations   │
     └───────┬────────┘ └──────┬───────┘ │ power,      │ └──────┬───────┘
             │                 │         │ fullscreen  │        │
             ▼                 ▼         └──────┬──────┘        │
     ┌──────────────────────────────────┐      │               │

     ┌──────────────────────────────────┐                      │

### 2.1. Проекты решения

| Проект | TFM | Ответственность | Зависит от |
|---|---|---|---|
| `WinterDesktop.Core` | `net8.0` | Модель настроек, геометрия/RNG, интерфейсы (`IWindowSource`, `IClock`, `IEffectHost`), `MonitorDescriptor`. Чистая логика, тестируема без Windows | — |
| `WinterDesktop.Settings` | `net8.0` | `SettingsStore`: чтение/запись JSON, атомарность, `.bak`, миграции, импорт/экспорт | Core |
| `WinterDesktop.SnowEngine` | `net8.0` | Генерация частиц, ветер/турбулентность, сугробы (heightfield), коллизии, варежка/лопата, снежки и снеговики | Core |
| `WinterDesktop.Platform` | `net8.0-windows` | Win32 P/Invoke: `SetWinEventHook`-трекер, `EnumDisplayMonitors`, `GetSystemPowerStatus`, детект fullscreen, автозапуск, DPI | Core |
| `WinterDesktop.Renderer` | `net8.0-windows` | Overlay-окно на монитор, D3D11 flip-swapchain, DirectComposition, Direct2D отрисовка частиц/сугробов/UI-оверлеев | Core, SnowEngine, Platform |
| `WinterDesktop.App` | `net8.0-windows` (WPF) | Composition root, tray, WPF-настройки, interaction wiring, жизненный цикл | все |
| `WinterDesktop.Core.Tests` | `net8.0` | Юнит-тесты ядра и снега | Core, SnowEngine |
| `WinterDesktop.Settings.Tests` | `net8.0` | Юнит-тесты хранилища (включая битый JSON) | Settings |

`SnowmanEngine`, `DecorationEngine`, `SnowCleaner`, `PerformanceManager`,
`InteractionEngine` появляются как отдельные папки/классы внутри `SnowEngine` /
`Platform` / `App` на своих этапах — с явными интерфейсами из `Core`, чтобы позже
вынести в отдельные сборки без переписывания потребителей. В MVP функции
взаимодействия (варежка, лопата, след курсора) уже живут в `SnowSimulation`;
адаптивное качество — в `App` поверх `PerformanceBudget` из `Core`.

### 2.2. Правила зависимостей

1. `Core` не знает ничего о Win32, WPF, Direct2D.
2. `SnowEngine` не знает о Win32 и о рендере: получает `WindowSnapshot[]` и
   публикует частицы/кромки; рендерер читает их только через `ReadOnlySpan` на том же
   потоке эффектов.
3. `Renderer` не содержит бизнес-логики: только интерполяция и рисование.
4. `Platform` не знает о снеге: только факты о системе.
5. `App` — единственное место, где всё сходится (composition root). Никаких
   статических синглтонов.
6. Обмен — через интерфейсы `Core`; события — через `INotifyPropertyChanged`
   (настройки) и типизированные callback-и (трекер).

## 3. Ключевые технические решения

### 3.1. Прозрачный overlay: DirectComposition + D3D11 flip-model swapchain

**Решение.** Один HWND на монитор: `WS_POPUP`, `WS_EX_NOREDIRECTIONBITMAP |
WS_EX_LAYERED | WS_EX_TOPMOST | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`. Содержимое —
D3D11 swapchain, созданный `CreateSwapChainForComposition` с
`AlphaMode = Premultiplied`, подключённый к окну через
`IDCompositionVisual`/`SetContent`. Рисование — Direct2D поверх DXGI-поверхности
backbuffer.

`WS_EX_LAYERED` нужен не для отрисовки (её даёт DComp, прозрачность — premultiplied
alpha), а для click-through: только у слоёного окна `WS_EX_TRANSPARENT` исключает
его из hit-testing, в том числе для окон других процессов. `SetLayeredWindowAttributes`
вызывается с `LWA_ALPHA = 255`, поэтому визуально ничего не меняет.

**Почему не альтернативы:**

| Вариант | Проблема |
|---|---|
| `WS_EX_LAYERED` + `UpdateLayeredWindow` | Копирование всего кадра через CPU/GDI каждый кадр; на 4K не тянет 60 FPS, нет GPU-ускорения → нарушает §3.10 |
| WPF `AllowsTransparency` | Программный рендер, полный экран 60 FPS нереалистичен |
| WinUI 3 | Тяжёлый деплой (WindowsAppSDK), избыточен для overlay, проблемы с topmost-слоем |
| D3D9Ex + `D3DImage` | Устаревший путь, лишний слой WPF-композиции |

**Риски и меры.** DirectComposition/D3D11 недоступны на очень старых драйверах →
fallback на WARP (программный D3D11) с автоматическим снижением профиля; если и это
не удалось — ошибка пишется в лог, поток эффектов завершается, а настройки, трей и
хранилище продолжают работать без визуального слоя (без падения).

### 3.2. Click-through

**Решение.** База: `WS_EX_LAYERED` + `WS_EX_TRANSPARENT` +
`SetLayeredWindowAttributes(..., 255, LWA_ALPHA)` и `WM_NCHITTEST → HTTRANSPARENT`.

Почему именно так:

- `WS_EX_TRANSPARENT` без `WS_EX_LAYERED` не влияет на попадание мыши: обычное
  (не слоёное) окно продолжает получать клики, даже если DComp-содержимое полностью
  прозрачно.
- `WM_NCHITTEST → HTTRANSPARENT` пропускает ввод только к окнам **своего потока**;
  для чужих процессов он не помогает.
- Вместе `WS_EX_LAYERED | WS_EX_TRANSPARENT` система исключает окно из hit-testing
  (`WindowFromPoint` возвращает окно под ним), поэтому клики доходят до любых
  приложений. `LWA_ALPHA = 255` сохраняет обычную композицию DComp-содержимого.

**Режим взаимодействия** (трей/окно настроек): перехват мыши избирательный.
`WS_EX_TRANSPARENT` снимается только у инструментов, которым нужен клик, — снежка и
снеговика, — и только рядом со снегом: в пределах 72 DIP от видимой кромки или фигуры,
а также пока в руке снежок. Варежка и лопата работают по глобальному опросу курсора,
поэтому клики не перехватывают и весь экран остаётся кликабельным. Решение принимается
раз в кадр на потоке эффектов (`OverlayHost.UpdateMouseCapture`), без пересоздания окна.
Окно настроек в этом режиме поднимается над overlay (`Topmost`), чтобы режим можно было
выключить мышью.

**Курсор.** `WM_SETCURSOR` не перехватывается: `DefWindowProc` ставит курсор класса
(стрелку). Раньше обработчик возвращал `TRUE` без `SetCursor`, и курсор «залипал» в том
виде, который был до входа на overlay (ожидание/занято/изменение размера).

**Аварийный выход.** Глобальная клавиша Ctrl+Alt+W (`RegisterHotKey` на message-only
окне, `MOD_CONTROL | MOD_ALT | MOD_NOREPEAT`) переключает режим и срабатывает поверх
любого приложения; клавиатуру overlay не забирает благодаря `WS_EX_NOACTIVATE`.
Если комбинацию уже занимает другая программа, неудачная регистрация пишется в лог,
а режим остаётся выключаемым с клавиатуры в окне настроек (Tab/пробел). Меню трея
в режиме взаимодействия может быть недоступно, если курсор попал в зону перехвата.

Дополнительно: позиция курсора **всегда** опрашивается раз в кадр
(`GetCursorPos`), поэтому «воздушный след» и варежка работают и в click-through
режиме — не требуется глобальный хук мыши (это ещё и приватнее).

**Полная пауза** (кнопка на главной и пункт трея) скрывает overlay-окна и
останавливает обновление симуляции. Ручная пауза и автопауза в полноэкранном
режиме — независимые флаги: снятие одного не возобновляет эффекты, пока активен
другой (`App.ApplySuspension`).

### 3.3. Отслеживание окон (Geometry-only)

**Решение.** `SetWinEventHook` с `WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS`
на диапазон `EVENT_OBJECT_CREATE..EVENT_OBJECT_HIDE` (фильтр `idObject == OBJID_WINDOW`,
`idChild == 0`). Для каждого события — чтение **только геометрии**:
`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` (точные видимые границы, без
невидимых рамок изменения размера), `IsWindowVisible`, `IsIconic`,
`DWMWA_CLOAKED` (виртуальные рабочие столы / UWP-фон), `WS_EX_TOOLWINDOW`.

Содержимое, заголовки, текст, изображения не читаются **никогда**. Заголовок окна
не используется в данных (только опционально для UI-списка «окно X», и это явное
действие пользователя; по умолчанию off).

**Производительность.** Перемещение окна генерирует десятки событий в секунду →
события складываются в флаг `_dirty` и обрабатываются пачкой на таймере трекера
(≤30 Гц), плюс снимок сцены пересобирается через `EnumWindows` (его порядок даёт
приблизительный z-order).

**Z-order.** Сугробы живут в одном topmost-слое, поэтому перекрытие окон выше
эмулируется: для каждого сугроба вычисляются видимые по X интервалы с учётом
прямоугольников окон, находящихся выше в z-order (порядок `EnumWindows`).
Полностью перекрытые участки не рисуются и не получают осадков. Снег под
«always-on-top» приложениями всё равно может быть виден — это ограничение
задокументировано в `KNOWN_LIMITATIONS.md`.

### 3.4. Модель сугробов

Heightfield на каждую кромку окна:

```
Ledge {
  IntPtr Hwnd;
  RectI Bounds;           // физические пиксели
  LedgeSide Side;         // Top | Bottom
  float[] Heights;        // N сэмплов, шаг SampleStep
  float[] Targets;        // накопление до насыщения
}
```

- N ≈ `width / 5px`, ограничено сверху (`MaxSamples = 512`) — предсказуемая память.
- Осадки: частица, пересекающая кромку, добавляет массу в ближайший сэмпл +
  распределение по гауссиане ±2 сэмпла (естественный холмик).
- Насыщение: `height += (target - height) * min(1, 7·dt)` (плюс сглаживание и
  ограничение крутизны), сверху жёсткий `MaxThickness` (§3.2).
- Уборка: варежка/лопата уменьшают `Targets` и `Heights`.
- Закрытие окна: масса конвертируется в падающие частицы (визуально «ссыпается»),
  затем сугроб удаляется.
- Максимальный суммарный объём снега — бюджет в условных единицах; при превышении
  старые сугробы не растут (не растёт память и стоимость отрисовки).
- Очистка кромки (`ClearLedge`) обнуляет оба массива и пересчитывает общую массу
  по оставшимся кромкам, чтобы счётчик не «застревал» из-за ещё не осевшей массы.

**Размеры сугробов.** Высота ограничена не только пользовательским пределом, но и
двумя множителями: `HeightVariation` (0.85…1.0, детерминированно от ключа кромки —
разные окна копят разное количество снега) и `CapAt(index)` — медленный профиль
вдоль кромки из трёх синусоид (≈400, ≈1100 и ≈3100 px). Профиль не превышает
`MaxHeight`, поэтому общий лимит толщины сохраняется, а насыпанный снег не
превращается в идеально ровную плиту.

**Одна поверхность на линию.** Верх панели задач обычно совпадает с низом рабочей
области, а окно может стоять подоконником на той же линии. Такие кромки не
создаются: `IsAtWorkAreaBottom` (допуск 3 px) оставляет одну поверхность, иначе на
одной линии рисовались бы два сугроба с разной кромкой.

**Низ рабочей области.** Видимость кромки рабочего стола тоже считается по сцене:
окно, которое доходит до линии низа рабочей области или уходит под панель задач,
вычитается из видимых интервалов. Иначе снег рисовался бы поверх содержимого окна
и выглядел висящим в воздухе. Окно, которое заканчивается ровно на линии, не
вычитается: это его нижняя кромка. Сама панель задач пропускается — она и есть
поверхность, на которой лежит снег.

**Рендер сугробов.** Все видимые интервалы всех кромок монитора собираются в один
`ID2D1PathGeometry` и заливаются одним `FillGeometry` с
`AntialiasMode.PerPrimitive`. Раньше каждая полоса heightfield рисовалась двумя
треугольниками меша с перекрытием 0.5 px, и на стыках полупрозрачная кисть
(`alpha 0.93`) накладывалась дважды — каждые 5 px появлялись вертикальные полосы.
Единый контур даёт сплошную заливку и мягкую кромку. Геометрия создаётся заново
каждый кадр: после `Close` объект нельзя открыть повторно (`D2DERR_WRONG_STATE`).

**Края сугроба.** У границы видимого интервала (край окна или перекрывающего окна)
высота плавно сходит на нет по smoothstep за `1.5 × толщины` (около 34°), но не
дальше 45% ширины интервала. Без этого сугроб обрывался вертикальной стенкой и
выглядел обрезанным; сход зависит от толщины, поэтому тонкий снег почти не
меняется, а большой сугроб получает длинный откос.

### 3.5. Время, физика и сглаживание

- Дельта времени берётся из `Stopwatch` на потоке эффектов. Если пауза/сон заняли
  больше 0,5 с, дельта заменяется на 16 мс — частицы не «телепортируются».
- Симуляция обновляется один раз на кадр эффектов (обычно 60 Гц) с переменным шагом;
  фиксированного аккумулятора 1/120 и интерполяции `prev → curr` в MVP нет.
  На практике при 30–120 Гц это незаметно, но при экстремальных просадках шаг
  физики растёт вместе с кадром.
- Кромки окон привязываются к новой геометрии при обновлении сцены (до ~30 Гц,
  коалесинг событий трекера). Позиция кромки при этом фиксируется на новом месте;
  плавного ease-out ~120 мс в MVP нет. При быстром перетаскивании окна сугроб
  двигается рывками вслед за обновлением сцены (задокументировано в
  `KNOWN_LIMITATIONS.md`).
- Ограничение FPS: `Present(1)` синхронизирует с вертикальной развёрткой; для 30/120
  поток «досыпает» до целевого интервала через `AutoResetEvent.WaitOne`.
- Сглаживание сугроба выполняется в пространстве высот (размытие с сохранением
  массы + ограничение крутизны), а не интерполяцией положения окна.

### 3.6. Многопоточность

| Поток | Что делает |
|---|---|
| UI (WPF STA) | Окно настроек, трей, команды. Ничего тяжёлого |
| Effects (один) | Свой message loop, все overlay-окна, D3D11/D2D/DComp, симуляция снега и отрисовка |
| WinEvent hook thread | Колбэки трекера, только помечают сцену «грязной» |
| ThreadPool-таймер (30 Гц) | Пересобирает снимок окон, раз в секунду проверяет мониторы |
| UI-таймер (1 Гц) | Питание, fullscreen, адаптивное качество, статистика |

Снег симулируется **один раз** на виртуальном экране (общая координатная система,
физические пиксели), а рендерер обходит окна мониторов и рисует пересечение со своей
областью. Так частицы естественно перелетают между мониторами и нет двойной работы.
Один поток эффектов владеет всеми устройствами и окнами, поэтому блокировки в кадре
не нужны; внешний код общается с ним только через неизменяемые снимки и очередь
команд.

### 3.7. Настройки

- Файл: `%LOCALAPPDATA%\WinterDesktop\settings.json`, пользовательские изображения —
  `%LOCALAPPDATA%\WinterDesktop\assets\`.
- Запись атомарная: `settings.json.tmp` → `File.Replace` (с `.bak`).
- Чтение: при `JsonException` файл переименовывается в `settings.corrupt-<ts>.json`,
  приложение стартует с дефолтами и пишет предупреждение в лог (§5).
- Любое изменение `SettingsStore.Current` → debounce 700 мс → сохранение.
- Схема версионируется (`SchemaVersion = 2`). Миграция 1 → 2 поднимает только
  значение по умолчанию `MaxThicknessDip` (18 → 24 DIP): ручной выбор не трогается.
  Миграция применяется при чтении, после чего файл сразу перезаписывается в новой
  схеме; отсутствующие поля заполняются значениями по умолчанию.
- При повреждении основного файла сначала пробуется `.bak`; если и он повреждён —
  дефолты, а копия повреждённого файла сохраняется для диагностики.
- Первый запуск (файла нет) сразу пишет дефолты и показывает окно настроек.
- Импорт/экспорт: тот же JSON, с валидацией и миграцией.

### 3.8. Производительность (§3.10)

`PerformanceBudget` (в `Core`) описывает бюджет:

```
Budget { int TargetFps; int MaxParticles; float QualityScale; bool AllowEffects; }
```

Профили: `Eco`, `Balanced`, `High`. Адаптивная логика живёт в `App`
(`ApplyAdaptiveQuality`): раз в секунду смотрит средний FPS за 0,5 с; при FPS < 42
понижает бюджет ступенями (до 2), после 12 секунд стабильных > 55 повышает обратно.
Питание: `GetSystemPowerStatus` → на батарее бюджет деградирует. Fullscreen:
foreground-окно покрывает свой монитор и не является shell → пауза рендера и физики,
но поток жив. Ручная пауза использует тот же механизм.

### 3.9. DPI

- Манифест: `PerMonitorV2` + `dpiAwareness` fallback. Все координаты слоя —
  физические пиксели (мониторы, окна, D2D).
- D2D-контекст не масштабируется (`Dpi = 96`), поэтому размеры частиц задаются в
  физических px, пересчитанных из «DIP-настроек» через `scale = monitor.Dpi / 96`.
  Иначе на 150% снежинки были бы крупнее/мельче, чем ожидает пользователь.
- WPF-окно настроек живёт по обычным правилам PerMonitorV2.

### 3.10. Надёжность и обработка ошибок

- Все Win32-вызовы, возвращающие `bool`/`HRESULT`, проверяются; ошибки логируются.
- Рендер-поток обёрнут в try/catch: `DeviceRemoved`/`NeedsRecreate` → пересоздание
  overlay-окон, после 3 ошибок кадра подряд — пересоздание графических ресурсов.
  Если инициализация не удалась, поток эффектов завершается, а настройки/трей
  продолжают работать (приложение не падает).
- `AppDomain.UnhandledException` и `DispatcherUnhandledException` → запись в лог;
  ошибки UI помечаются обработанными, чтобы одна команда не роняла приложение.
- Дисплеи: трекер раз в секунду перечитывает конфигурацию мониторов; при изменении
  набора/разрешений overlay-окна пересоздаются, снег сохраняется, сугробы
  перепривязываются.
- Сон/пробуждение: отдельного обработчика питания нет; скачок времени ограничен
  16 мс, потеря устройства обрабатывается как `NeedsRecreate`.
- Завершение: `NotifyIcon` dispose, снятие хуков, `D3D11` dispose, `settings.Flush()`.

### 3.11. Логирование

Собственный минимальный file-logger (без сторонних зависимостей):
`%LOCALAPPDATA%\WinterDesktop\logs\app-YYYYMMDD.log`, ротация 7 файлов, уровни
Info/Warn/Error, размер ограничен. Телеметрии нет (§7).

### 3.12. Снежки и снеговики (этап 3, первый инкремент)

Обе механики — часть `SnowSimulation` и используют общий heightfield сугробов, поэтому
не появляется второй физический мир и не растёт стоимость кадра.

**Снежок.** `BrushTool.Snowball`:

1. Нажатие в пределах кромки вызывает `TakeSnow`: из `Heights` и `Targets` вычитается
   площадь будущего шара. На тонких полосках снег подгребается с более широкой полосы
   вдоль кромки; если снега нет совсем, показывается только снежная пыль.
2. Пока кнопка нажата, шар удерживается у курсора (`SnowBall` с флагом удержания).
3. При отпускании вычисляется скорость курсора за последние кадры; она становится
   начальной скоростью шара. Дальше — гравитация и ветер, общие с частицами.
4. Столкновение с кромкой (`Vy >= 20`) добавляет депозит в heightfield и создаёт
   брызги; столкновение с телом окна даёт только брызги. Шар живёт до попадания или
   до выхода за монитор.
5. Лимит — 32 шара; при превышении новые не создаются.

**Снеговик.** `BrushTool.Snowman`: три последовательных нажатия по сугробу добавляют
шары 1–3. `SnowFigure` хранит геометрию (радиусы, смещения, декор) и ключ кромки.
Фигура статична; её основание привязано к Y-координате кромки и обновляется вместе с
ней, поэтому снеговик «едет» вместе с окном. Лимит — 24 фигуры.

**Сохранение.** `SnowSimulation` поднимает `SnowmenChanged` со снимком фигур.
`OverlayHost` передаёт снимок в `App`, который маршалит его в UI-поток, пишет
`SnowmenRecord` в настройки и вызывает `SaveSoon`. Сигнатуры сравниваются, чтобы
событие не порождало цикл сохранений. При старте движок восстанавливает фигуры один
раз за запуск: по ближайшей кромке монитора, иначе по низу рабочей области
(`LedgeKey = 0`). `ClearAllSnow`/`ClearMonitor`/`ClearWindow` удаляют фигуры
и уведомляют об изменении пустым списком.

**Рендер.** Порядок: сугробы → снеговики → снежки → снежинки. Для фигур и шаров
используется `AntialiasMode.PerPrimitive`; добавлены кисти контура, тени, угля,
морковки и веток.

**Режим.** Снежок и снеговик работают только при включённом режиме взаимодействия;
лопата — всегда.

### 3.13. Гирлянды (этап 3, второй инкремент)

Гирлянды не смешиваются с физикой сугробов: это отдельный слой геометрии, который
пересобирается только при смене сцены или настроек. В кадре движок ничего не
пересчитывает и не аллоцирует, рендер только рисует готовые точки.

**Модель.** `Garland.cs` содержит:

- `GarlandBulb` — `readonly record struct` с X/Y, индивидуальной фазой и индексом на
  нити (индекс задаёт цвет в палитре);
- `GarlandString` — владелец (HWND), масштаб DPI, Y кромки и провода, шаг, радиус,
  базовая фаза и массив видимых лампочек;
- `GarlandTiming` — чистая математика: `Brightness(animation, phase, time, speed)`
  возвращает 0…1, `PhaseFor(key)` детерминированно раскладывает фазы окон.

**Раскладка.** `SnowSimulation.RebuildGarlands` вызывается из `UpdateScene` после
`RecomputeVisibility`. Для каждого окна, пригодного для кромок:

1. Берётся `Bounds.Top`; окна панели задач и оболочки, а также кромки вне
   виртуального стола пропускаются.
2. `ComputeGarlandSpans` вычитает из `[Left, Right]` интервалы окон выше по z-order,
   пересекающиеся с полосой вокруг кромки. Для этого используется общий
   `SubtractFrom` — та же операция, что и для видимости сугробов.
3. `AppendGarlandBulbs` раскладывает лампочки с постоянным шагом внутри каждого
   видимого интервала; узкий интервал получает одну лампочку по центру.
4. Жёсткий предел `MaxGarlandBulbs = 4096` обрезает раскладку на сотнях широких
   окон. После лимита цикл по окнам прекращается.

**Рендер.** `SnowRenderer.DrawGarlands` рисует в порядке: провод и подвесы → ореол →
ядро и блик. Провод не соединяет лампочки через скрытый участок: соседние точки
соединяются, только если расстояние между ними не больше `Spacing * 1.6`. Яркость
лампочки берётся из `GarlandTiming`, поэтому режимы анимации не дублируются в
рендере. Палитры — статические массивы `Color4`; кисть перекрашивается через
`ID2D1SolidColorBrush.Color`, чтобы не создавать ресурсы в кадре.

**Настройки.** `GarlandsSettings` (`enabled`, `palette`, `animation`, `speed`,
`spacingDip`, `bulbSizeDip`, `glow`) входят в `AppSettings`, сериализуются вместе с
остальными секциями и клэмпятся в сеттерах. Схема настроек остаётся 2: отсутствующая
секция `garlands` заполняется значениями по умолчанию, миграция не нужна. По
умолчанию гирлянды выключены.

**UI.** Восьмая вкладка «Гирлянды» между «Накоплением» и «Инструментами»: включение,
палитра, режим, скорость, шаг, размер и свечение. В трее — пункт «Гирлянды».
`OverlayStats` дополнен `GarlandCount` и `GarlandBulbCount`; строка статистики
показывает число нитей и лампочек.

## 4. Формат данных снега (граница SnowEngine ↔ Renderer)

Рендерер и симуляция живут на одном потоке эффектов, поэтому граница максимально
дешёвая — без сериализации и копирования кадра:

```csharp
public ReadOnlySpan<SnowParticle> ActiveParticles { get; } // X, Y, Radius, Alpha, Shape…
public IReadOnlyList<Ledge> Ledges { get; }                 // Heights, VisibleSpans, EdgeY…
public IReadOnlyList<SnowBall> Snowballs { get; }           // X, Y, Radius, Vx, Vy, Held
public IReadOnlyList<SnowFigure> Figures { get; }           // позиция основания, шары, декор
public event Action<IReadOnlyList<SnowmanRecord>>? SnowmenChanged; // снимок для сохранения
```

Рендерер только читает эти данные (`SnowRenderer.Render(window, simulation, settings)`).
Мутировать состояние движка из рендерера нельзя: все команды (настройки, очистка,
пауза) проходят через очередь `OverlayHost` и выполняются на том же потоке до кадра.
Это даёт ноль аллокаций в кадре и исключает гонки без блокировок.

## 5. Почему это поддерживаемо

- Новый эффект = новый «слой» рендера + опциональный движок за интерфейсом из `Core`.
- Настройка = свойство в `AppSettings` + биндинг в WPF + чтение в движке.
- Один источник истины по времени (`IClock` в `Core`) → тестируемость без sleep.
- Вся математика (ветер, насыщение сугробов, коллизии) — чистые функции в `SnowEngine`,
  покрыты юнит-тестами без GPU и без окон.

## 6. Известные архитектурные компромиссы

1. Один topmost-слой → нет настоящего per-window z-order; эмуляция по X-интервалам
   (см. §3.3). Задокументировано.
2. Живые обои (Этап 4) требуют трюка с `WorkerW`, чтобы оказаться под иконками
   рабочего стола — это недокументированный контракт Explorer; предусмотрен fallback
   на «нижний слой поверх иконок» и явная деградация. Решение валидируется на Этапе 4.
3. Гирлянды и сугробы рисуются в одном слое, поэтому поверх окон, а не «внутри» них.
4. macOS-порт потребует нового `Renderer` (Metal) и `Platform`, но `Core`+`SnowEngine`
   переносятся без изменений.
5. Позиция кромки не интерполируется: при перетаскивании окна сугроб обновляется
   вместе со снимком сцены (до ~30 Гц). Визуально это заметно только при быстром
   движении окна; ценой была бы задержка привязки снега к окну.
6. Ручная пауза намеренно не сохраняется в настройках: после перезапуска приложение
   возвращается к активному снегопаду.
7. Снеговик привязан к кромке, а не к свободной точке экрана: у него нет собственной
   физики падения и опоры. Это сознательно — фигура не «дрожит» и не сползает, но
   восстановление возможно только на существующей кромке или на низу рабочей области.
8. Снежки не взаимодействуют со снеговиками и не отскакивают от окон: попадание в
   тело окна даёт только брызги. Полноценная физика шаров — отдельная задача.
